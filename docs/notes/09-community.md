## 1. Data model (and why)

### posts
Key columns: `id, user_id (author), author_name/author_university/author_major (display snapshot), title, body, kind, subject (legacy, unused), tags text[], repost_of (points at the original for a repost), points_business_key (generated by 0008 and immutable), like_count/comment_count/favorite_count/repost_count (denormalized counters), image_url/audio_url, created_at/updated_at`.

Design points:
- **Author snapshot fields**: the community needs to show "other people's" names/schools, but `profiles` is owner-only (you can only read your own). Two options: open up profiles reads, or "snapshot" the author info onto the post. We chose the latter — more private (no email exposure, etc.), at the cost of old posts not updating after a rename (acceptable).
- **Denormalized counters**: the feed shows like/comment counts. A `count(*)` each time is too slow, so counters live on the post row and are maintained by triggers (see below).
- **A repost is a post**: `repost_of` points at the original, and a repost is just an ordinary post. Pros: reposts naturally enter the feed and can be liked/commented again; cons: the original has to be fetched and embedded at render time.

### comments / post_likes / post_favorites / follows / tags
- `comments(post_id, user_id, author_name, body, points_business_key)`; multiple comments by the same user on the same stable target content share one points claim.
- `post_likes(post_id,user_id,points_business_key)` / `post_favorites`: composite primary key `(post_id, user_id)` — naturally prevents duplicate like/favorite rows; 0008's stable keys also dedupe rewards across recreated identical content/duplicate posts.
- `follows(follower_id, following_id)` composite primary key.
- `tags(kind, value)` composite primary key, `kind ∈ university|major|subject|tag` — the global tag pool (see 0006).

## 2. RLS: the first "publicly readable" module

Every earlier table was owner-only. Community is different: **posts/comments are readable by everyone, but only the author can write, edit, or delete**.

```sql
-- posts
create policy posts_select_all  ... for select to authenticated using (true);          -- anyone can read
create policy posts_insert_own  ... for insert with check (user_id = auth.uid());       -- can only post as yourself
create policy posts_update_own  ... for update using (user_id=auth.uid()) with check(...);-- can only edit your own
create policy posts_delete_own  ... for delete using (user_id = auth.uid());            -- can only delete your own
```
- comments work the same way (public read + author write/delete).
- **likes/favorites are owner-only** (`for all using user_id=auth.uid()`): you can only see/change your own like records. "How many likes does this post have" does not query the likes table but uses the post's `like_count`. That shows totals without leaking "who liked whom".
- follows: `select using (follower_id=auth.uid() or following_id=auth.uid())` — you can see the people you follow + your own followers.
- Production 0039 adds a column allowlist on top of the row-level owner policies: INSERT only accepts content columns and `repost_of`; content UPDATE accepts `title/body/kind/subject/tags/image_url/audio_url`. `user_id`, author snapshots, the four counters, repost, points key, and timestamps are maintained by the database; production 0052–0053 finally revoked authenticated UPDATE on `updated_at`.

> Rule of thumb: **decide read permissions by "should this data be public"**, not a blanket owner-only. Write permissions are always pinned to `auth.uid()`.

## 3. Triggers (server logic, all `security definer`)

Why they all need `security definer`: triggers must change "other people's" rows (a liker increments the post owner's counter, notifications go to the post owner), and the caller has no RLS permission to change other people's rows; `security definer` makes the function run as its owner (high privilege), bypassing RLS.

### 1) Counter maintenance (0005 `_bump_counts`)
`after insert or delete on post_likes/post_favorites/comments`:
```
d := (insert ? +1 : -1); pid := coalesce(new.post_id, old.post_id);
update posts set like_count = greatest(0, like_count + d) where id = pid;  -- column chosen by table name
```
`greatest(0, …)` keeps concurrency/anomalies from pushing counters negative.

### 2) Author snapshot + anti-forgery (0005 `_post_author` / `_comment_author`)
`before insert on posts`:
```
select username, university, major into new.author_name, new.author_university, new.author_major
from profiles where id = auth.uid();
```
On INSERT it ignores any author_* sent by the client and forces the real profiles values. Production 0039 also protects UPDATE with column grants + the `_protect_post_trusted_fields` trigger: `updated_at` only refreshes when content changes, so pure counter-trigger changes never fake a "just edited".

### 3) Repost counter (0005 `_bump_repost`)
`after insert/delete on posts`: if `repost_of` is not null, `repost_count ±1` on the original.

### 4) Points + interaction notifications (0006; points replaced in 0008)
- `_add_points(uid, d)` is retired and revoked from clients/service-role; `profiles.points` is rebuilt from the sum of append-style `point_entries`.
- `_set_point_event(...)` is the only points state-transition entry point: serialized per stable business key, activation writes a positive entry, deletion/un-completion writes a negative entry, and retrying the same state is a no-op; clients have no EXECUTE.
- `_notify(uid, type, title, body)` still writes notifications from trusted triggers/service-role, but client EXECUTE is revoked.
- Triggers:
  - `_on_like` (insert/delete): **+1** for the first valid non-self-like claim, **-1** once every same-key relation is deleted; notifies the post owner.
  - `_on_comment` (insert/delete): **+2** for the first valid non-self-comment claim, **-2** once every same-key comment is deleted; notifies the post owner.
  - `_on_fav`: notifies the post owner (no points).
  - `_on_post` (insert/delete): **+10** for a valid original claim and **+3** for a repost; reversed once every same-key post is deleted, and a repost notifies the original author.
  - `_on_follow`: notifies the person followed.

The original-post key is the SHA-256 of author + normalized title/body/kind/subject/sorted tags; reposts anchor to the root original key; likes/comments anchor to the target post's immutable key + actor. The database generates these fields before insert and rejects changes to `repost_of` or an already generated key.

Note: these triggers write notification titles/bodies in fixed Chinese text. The Web client recognizes these known shapes by `type` and renders them in the current UI language (see `notificationText` in `notifications.ts`).

### 5) Automatic global tag collection (0006)
- Changing university/major on `profiles` or creating a `courses` row → upsert into `tags` (`on conflict do nothing`).
- The migration back-fills historical data once.
- Media: creates the public bucket `community-media` (writable only in your own folder, publicly readable).

## 4. Frontend module structure (`community.ts`)

### Module-level state
```
let sb, USER, toastFn;                 // injected: client, current user, toast
const me = {id,name,university,major};  // my profile (filled by ensureMe)
const followingIds = new Set();         // ids of people I follow
const globalTags = {university:[],major:[],subject:[],tag:[]}; // global tags
const state = { loading, error, filter, mineTab, counts, posts, liked:Set, faved:Set, originals:{} };
let feedEl;                             // current mount container
```
- `filter`: `all | following | mine | question | tip | note_share | t:<tag value>`.
- `liked/faved`: ids of posts in the current list I have liked/saved (for highlighting; updated only after the database write succeeds).
- `originals`: map of reposts' originals (id → original post), used for embedded rendering.

### Lifecycle
`mountCommunity(el)` → `renderFeed()` (skeleton first) → `await ensureMe()` (fetch the current account's profile/follows/tags) → `load()` (fetch posts by filter). Every init clears the previous account's `me/followingIds/globalTags/state`; async operations use `sessionVersion` to discard late responses after an account switch.

### Key functions one by one

**ensureMe()** — fetches three things concurrently: my profile, my follow list, and global tags; fills `me / followingIds / globalTags`. `meLoaded` ensures it is fetched only once per account session, and the next init clears it.

**load()** — the main feed query. Builds the supabase query from `filter`:
- `question/tip/note_share` → `.eq("kind", f)`
- `t:xxx` (tag) → `.contains("tags", [value])` (Postgres array containment, PostgREST `tags=cs.{value}`)
- `following` → takes `followingIds`; empty means an empty list, otherwise `.in("user_id", ids)`
- `mine` → delegates to `loadMine()`
After fetching, `hydrate()` adds interaction state, then `renderFeed()`.

**loadMine()** — the "Mine" page. First queries three `count`s concurrently (posts/following/followers, `head:true` for counts only); then fetches the list by `mineTab`:
- `posts`: mine, not reposts (`.eq(user_id).is(repost_of,null)`)
- `reposts`: mine, reposts (`.not("repost_of","is",null)`)
- `replies`: my comments → distinct `post_id` → then fetch those posts
- `liked/faved`: query my post_likes/post_favorites (RLS only returns mine) → take post_id → fetch the posts

**hydrate(posts)** — enriches a batch of posts with: ① my likes/saves on them (query post_likes/post_favorites `in(ids)`; since RLS only returns mine → the `liked/faved` sets); ② reposts' originals (collect distinct `repost_of` → query → fill `originals`).

**renderFeed()** — two layouts: when `filter==="mine"` it renders "Mine" (stats + sub-tabs + cards); otherwise the regular feed (filter chips + cards + suggested follows on the right). Ends with `wire(feedEl)` to bind events.

**Rendering helpers**: `feedChips()` (fixed filters + `tagChips()` global tags), `suggestions()` (picks unfollowed authors from the current feed), `postCard(p,big)` (author row + embedded repost + title/body + `mediaBlock` + tags + `actionBar`), `authorRow` (with "Follow/Following" and "Edit/Delete (own)"), `actionBar` (like/comment/repost/save + counts + highlighting). All copy goes through `localize(english, chinese)`.

### Event model (key design)
```
function wire(scope){ scope.querySelectorAll("[data-cm]").forEach(el =>
  el.onclick = e => { e.preventDefault(); e.stopPropagation(); handle(el.dataset.cm, el); }); }
```
- My action buttons carry `data-cm="like|fav|repost|follow|edit|del|..."`, handled by this module with **`stopPropagation`**.
- The post card itself carries `data-go="post"`, handled by the **app shell's global click delegation** (legacy `app.ts`) to navigate to the detail page.
- Together: clicking empty card space → bubbles to the shell → opens the detail; clicking like → `stopPropagation` stops it → likes without navigating. This is "reuse the shell's routing + handle actions yourself".

### Action data flow (using like as the example)
```
Like span (data-cm=like) → wire's onclick → handle("like") → toggleLike(id)
toggleLike: await post_likes insert/delete → check { error } and sessionVersion
           → only on success update the liked set and local like_count → renderFeed()
DB triggers: likes_cnt updates like_count (authoritative); _on_like activates/reverses the same points claim and notifies the post owner when it isn't a self-like
```
`toggleFav/toggleFollow` likewise update the UI only after the backend succeeds. `addComment/delComment` use "remount `mountPost` after a successful write" (few comments, simple and reliable). `delPost` uses the in-app `confirmDialog` for confirmation. Every path surfaces Supabase failures and no longer treats `{ error }` as success.

The production 0039 app additionally calls the owner receipt after successful post, repost, like, and comment writes. When the actual reward is 0 with reason `daily_cap`, it shows a toast immediately, and the database guarantees at most one persistent notification per type per day; a receipt network failure only shows a non-blocking notice and never rolls back a successful community action. The +N the frontend shows is not the source of truth; Profile still refreshes from the ledger projection.

### Posting/editing (composer)
- One modal handles both create and edit (depending on whether `existing` is present).
- **Multi-select tags**: `drawTags()` renders `globalTags` (🏫 university/🎓 major/📚 subject/# custom) as toggleable chips, and clicking adds/removes them from the `selected` set; pressing Enter in the custom input → adds to `globalTags.tag` + `selected` + `insert tags`.
- **Attachments**: `pick(accept,set)` creates a hidden `<input type=file>` → `uploadMedia(file)` uploads to `community-media` and takes the public URL → stores `imageUrl/audioUrl`; `drawMedia()` shows a preview + remove.
- Save: build `row={kind,title,body,tags:[...selected],image_url,audio_url}` → edit with `update().eq(id)` / create with `insert(row)`; a `saving` lock prevents duplicate submits. Author fields are filled in by triggers, not sent from the frontend.

### Repost (repostModal)
The modal takes an optional comment → `insert({repost_of:id, body, tags:original's tags})`. It is itself a post, so triggers add to the original's repost count, notify the original author, and give me +3 points.

### mountPost(el, postId) (detail)
Fetches the post (`.eq(id).single()`) + `hydrate([post])` + fetches comments (`.eq(post_id).order`) → renders the large card + comment box + list. After submitting/deleting a comment it **remounts itself** to refresh.

## 5. Pitfalls / trade-offs
- **Public read vs owner-only**: Community is the first to use `using(true)`; writes are still strict. Showing other people's info relies on snapshots, without opening profiles reads.
- **Current points integrity**: 0008 fixed net-amount farming via unlike/re-like, comment/post delete-and-recreate, reposts, and task un-complete/redo; the same business key has only one active claim, and deletion/un-completion writes a reversal. Production 0039 adds daily award caps of 3 original posts, 10 reposts, 10 comments, and 20 likes, freezing the first decision; the coordination scan only writes pending signals, and only manual suppress/restore can reverse the same root content chain. Points are still never currency or commercial entitlement.
- **Legacy balance boundary**: pre-migration points were recorded by 0008 as `legacy_opening`, and their origin cannot be proven from the old tables; on 2026-07-21 the owner decided to zero them all with equal reversals appended by 0009.
- **UI vs authoritative values**: interaction UI only changes after the database succeeds; denormalized counters remain authoritative in the trigger-maintained columns, and the next load overwrites the local display.
- **Navigation relies on shell delegation**: action buttons must `stopPropagation`, or they will also trigger the card's `data-go` navigation.
