# Courses: English vocabulary learning

> **About this document**
> - **Contents**: Explains the data boundary of independent learning courses, text import and editing, four-stage learning, review/exam mastery, the `learned_at` rule, sharing/market, and the current acceptance status.
> - **Purpose**: The technical retrospective and maintenance entry point for the first version of Courses; the final product scope is still defined by the project blueprint.
> - **When to update**: When the course contract, database, learning state machine, points/badges, Azure Speech/OpenRouter, sharing/market, or test boundaries change.
> - **Status baseline**: 2026-08-11. The Courses feature migrations 0011–0038 are released, and the current overall production history is at 0043; 0037–0038 add Chinese voice input for translations and the service-only STT quota boundary, and 0035–0036 harden `learned_at` into an exact trigger projection of the two exam timestamps. Courses AI file import and the other three course categories must still not be described as implemented.

## 1. Boundary and entry points

Courses uses the independent `learning_*` model and does not reuse Materials' `courses/materials`. The Courses sidebar shows an empty state and "Create course" by default; the category picker keeps four categories — English vocabulary, knowledge points, reading comprehension, question bank training — and only English vocabulary can be created in the first version. Market contains the still-demo Note Market and the Course Market that reads real snapshots.

Courses, learning/review, public sharing, and Course Market share the Web app's `nalanda-locale` state: without a saved preference it defaults to English, and users can switch to Chinese in the top bar, persisted in the browser. Course-specific CSS only defines the editor, card grid, and learning state machine layout; fonts, colors, base buttons/forms/cards/modals, light/dark themes, and interaction states all reuse the design tokens in `@nalanda/ui/nalanda.css`, and no separate brand theme may be created.

The file entry point lists PDF, DOC/DOCX, JSON, Markdown, HTML, and images, but only shows "AI parsing coming soon" and never uploads, parses, or calls a model. The only reliable input today is **manually pasted text**, either pasted unit by unit or as one whole multi-unit word list.

## 2. Text parsing and structured editing

- Rules: blank lines are ignored, each line is split into English and translation at its last ASCII space, and translations are further split by `/`; `take part in` followed by two slash-separated Chinese translations is a valid phrase line.
- The parser returns the line, column, error code, and message, covering a missing separator, empty translations, consecutive `/`, duplicate translations, invalid English, overlong values, normalized duplicates within a unit, and XSS/Unicode boundaries; any error blocks saving and highlights the original position.
- Courses with units can choose "Paste unit by unit" or "Whole multi-unit word list". Whole mode automatically recognizes `Unit`, `Lesson`, `Chapter`, `Module`, and `Section` headings ending in a number, letter, or Roman numeral (for example `Starter Unit 1`), as well as numbered Chinese unit/lesson/chapter headings; any custom name must be written as `[Custom name]` or a Markdown heading `# Custom name`, otherwise it is treated as an entry. This explicit rule removes the ambiguity of "is this line a heading or an entry".
- Whole mode requires a unit heading before the first entry, and validates empty units, 1–80 character unit names, and at most 100 units; entry error lines/columns still point into the whole original text and are not reset to positions relative to the unit.
- The course name is required; each course has 4–2,000 distinct normalized words/phrases, at most 100 units, and at most 10 translations per word. Unit-less mode still stores a hidden default unit.
- The editor can change the course name, unit names, English, separate translation text blocks, and manual IPA, can delete and move across units, and sorts with dnd-kit by mouse/touch/keyboard, with explicit move up/down buttons as well. Each translation has its own input and delete button and can be added one at a time up to 10, so a two-meaning translation is no longer shown as one indivisible field.
- Each unit in Review/Edit Course can add words one at a time or open the "Bulk paste words" panel to append a whole word list. Appending uses the same parsing rules; if a term duplicates the unit's existing normalized English it returns `DUPLICATE_EXISTING_TERM`, and when there is any error or the course would exceed 2,000 words, nothing is partially written into the editing state.
- CMUdict converts American ARPAbet→IPA inside the API; phrases are combined word by word. When it can't be resolved, `null` is saved and "IPA to be added" is shown.
- The whole course is saved in one `learning_upsert_course` transaction. Changing the English resets every learning ability and both exam facts; changing translations resets the translation ability and the spelling exam fact, and changing IPA resets the pronunciation ability and the pronunciation exam fact; any exam fact becoming invalid clears `learned_at`. Reordering, moving, and renaming reset nothing and don't end the active session. When units/words are added or removed or word content changes, the transaction marks the old active session terminated and keeps the existing attempts instead of deleting answer facts; the user then starts a new session from the new content.

### 2.1 Long-content scrolling convention

The production app shell is fixed to one screen height; `.main` and `.content` must both keep `min-height: 0`, with `.content { overflow-y: auto; }` handling page vertical scrolling uniformly. The Courses create, Review/Edit, learning, and market pages must not create conflicting full-screen heights or an outer `overflow: hidden`; on long pages, the bottom "Add word", "Bulk paste words", "Add unit", and save actions must be reachable through that same scroll container. Modals still use their own bounded height and internal scrolling, and background page scrolling must never be mistaken for modal scrolling.

## 3. Learning and resuming

Unfinished sessions resume independently by request intent rather than being forced unique per course. Initial learning uses course + unit as the intent; ad-hoc review also includes the scope and the sorted test skills; scheduled review uses the schedule ID. So after pausing Unit 1's initial learning you can start reviewing Unit 2 with both kept; concurrent starts with the same intent still return the same session through an advisory lock and a partial unique index. The course card shortcut continues the most recent activity, and after finishing an ad-hoc review you see the still-unfinished initial learning again. The session's stage, position, retry pool, word items, and actual answers are all written to the database, so a refresh or another device can continue.

The in-progress page distinguishes two exit semantics: "Pause and return" only leaves the page, and the original active session keeps resuming by intent; "Cancel learning" needs confirmation and, through a NestJS/service-role RPC, locks and terminates the session and advances the revision, after which the same intent creates a new session. Confirmed attempts, error counts, and mastery history are kept, and unfinished review schedules can be restarted; after the server confirms the cancellation, the browser only clears that account's not-yet-synced IndexedDB answers for that session and never other learning sessions.

1. **Recognize words**: shows the English, IPA, all translations, and pronunciation in order; read-aloud scoring is optional. The overall `PronScore` passes at 70 by default, and low scores durably enter this stage's retry pool; the result page shows the real threshold and retry status, and offers "Read again and score" immediately, where a passing re-read removes the retry item.
2. **Pronunciation memory**: at most five words per batch, with the audio column and the word column shuffled separately; choosing the word matching a pronunciation submits immediately and shows the result on the chosen item. A correct answer advances automatically after a short animation; a mismatch is recorded against the target word and enters the next round's retry pool, and the error state stays until the user clicks "Next question".
3. **Translation memory**: with one translation, clicking an option judges immediately; with multiple translations, confirm each correct item in turn, the last correct item submits automatically, and any wrong item is judged wrong immediately. Distractors come from other translations in the course; correct answers advance automatically, while wrong answers keep showing the wrong option and the correct answer until a manual "Next question", without restoring the two-step Check/Continue confirmation.
4. **Spelling memory**: type after the pronunciation plays. Both the Web app's instant judgement and the database's authoritative judgement apply NFKC, Unicode whitespace collapsing, and ASCII case folding to the answer and the course's original `term`, and compare, using the same punctuation set, the original text, the text with punctuation removed, and the text with punctuation treated as spaces. Answers that only omit, replace, or add punctuation are judged correct, for example `You're welcome.` / `Youre welcome!` and `check-in` / `check in` / `checkin`; letters, digits, word order, and inter-word spaces with no punctuation involved must still be correct, so `ice cream` / `icecream` is wrong. Enter or one submit fixes the answer. When starting a session that includes spelling, you can choose no time limit or a 3–300 second limit; the limit starts when the spelling input actually becomes answerable, and when it reaches zero it auto-submits the current content (possibly empty) exactly once. A translation pre-test can also be turned on: the user first types the translation, and since 0037 the right end of that input offers Chinese voice input available only there; while recording it shows a live waveform, and when Fish Audio recognition finishes it only fills the input without submitting, so the user can edit it. The final text is still judged semantically by the server; only when correct does the spelling input appear and timing start, while a wrong answer creates one spelling error for that word. Correct answers advance automatically; for any error, the character differences, the correct English, and every translation stay visible until the user clicks "Next question".

Every course screen that captures user audio shares the same live waveform, including the optional read-aloud feedback in the recognition stage, the pronunciation exam, and translation voice input. The waveform is derived on the fly from the current browser audio frames and is never saved as a learning fact; the translation STT's audio/text never enters Cache Storage, Supabase Storage, or the database. The speech recognition result itself has no grading authority; only the existing translation assessment of the text the user edits and explicitly submits can create server-side facts.

Each test stage runs "all words in the first round → this round's error pool → the next round's error pool" until everything passes. Since 0027, when the spelling stage ends a round with wrong words, it does not automatically enter the retry round: the session durably stores `awaitingRetryConfirmation/retrySummaryIds/retryFromRound`, and the UI lists all of this round's wrong words with their English, IPA, individual translations, and pronunciation. The last few questions must first be confirmed by the server; only when the user then clicks "Shuffle and start the next round" does the service-role RPC advance the revision, clear the confirmation flag, and deterministically shuffle the retry words by session/round. During confirmation, ordinary attempts and translation judgement claims are both rejected by a database trigger, and a refresh or another device stays on the same review page.

Recognition progress and every answer are updated atomically by owner-validated service-role RPCs, and clients cannot forge sessions, attempts, or progress directly.

### 3.1 Exam mode

The course card has a separate exam entry point. The user chooses one unit, any 1–2,000 words, the exam type, and a first-round accuracy requirement of 1–100%, defaulting to 90%; since 0031 the database verifies the selected IDs all belong to the owner/course/unit and fixes them in the session, and without a custom selection the whole unit is used. Both exam types durably shuffle the first round, and the page shows `examCorrect/examAnswered/examAccuracyPercent` from the server state in real time, recoverable after a refresh.

- **Spelling exam (production):** fixed `skills=["spelling"]` with the translation pre-test on, and the spelling time limit still selectable. A wrong translation directly creates one authoritative spelling error for that word; a correct translation continues to spelling, so each word produces exactly one score-determining spelling attempt in the first round.
- **Pronunciation exam (production 0029+):** fixed `skills=["pronunciation"]`. The page first shows only the English word and IPA; after the user reads it aloud, the existing Azure Pronunciation Assessment returns a `PronScore`, and the question counts as correct only when the word score reaches the server's `AZURE_SPEECH_PRONUNCIATION_PASS_SCORE` (default 70). After scoring, whether right or wrong, the word, overall score, phoneme feedback, translations, and the standard TTS button stay on screen, and the local view advances only when the user clicks next word. Provider/microphone failures create no attempt and don't count as errors.

Passing depends only on the accuracy of the full first round; later error rounds are practice and can never turn a failed exam into a pass. Even if the first round met the threshold, the end-of-round review and all wrong-word retakes must still be completed. Each round's wrong-word page shows the English, IPA, separate translations, and standard pronunciation; the pronunciation exam also shows that round's scores. After the user confirms, the general service-role retry-round RPC shuffles by session/round and advances the revision. Once the last retry word is answered correctly, the session automatically enters `completed` whether or not the first round met the threshold; since 0031 it also writes `practiceCompleted=true`, so history clearly expresses "exam not passed but every wrong answer has been corrected".

Only after the session enters `completed` with a first-round `examPassed=true` does a database trigger write the corresponding exam fact for the session items selected this time, by `examKind`: the spelling exam writes `spelling_exam_passed_at` and keeps the initial translation/spelling flags; the pronunciation exam writes `pronunciation_exam_passed_at` and keeps the initial pronunciation flag. Passing either exam alone never writes `learned_at`; only when both exam timestamps of the same word are non-null does 0033 project the later pass time as `learned_at`, followed by the existing growth/course-completion projection. Finishing error practice below the threshold only ends the session and writes `practiceCompleted`, never exam facts or `learned_at`; the user can start a new exam. Exams never fake any review dates, and do not change the existing idempotency rules for points, badges, or qualifying courses.

### 3.2 Custom word selection and exam history (production 0031–0034)

Ad-hoc reviews, reviews entered from Schedule, and both exam types show a scrollable word list within the unit, selecting every word in the current `all/unlearned` scope by default, and the user can select all, clear, or tick any words. The Web app submits `wordIds`; NestJS only does UUID/count/dedupe pre-checks, and the database selected-session RPC then verifies the user, course, unit, scope, and every word ID. Ad-hoc reviews/exams include the SHA-256 of the sorted set in the `resume_key`, so different selection intents are never resumed by mistake; Schedule still resumes by its unique schedule ID, and the selection at first start is fixed in the session items and state and can never be silently replaced on resume. Later course edits still end the affected active sessions per the existing rules.

"Exam history" at the top of Courses reads the owner's latest 100 exam sessions. The list distinguishes in progress, cancelled, passed, and not passed but practice completed, and the detail shows the exam type, first-round/required accuracy, the final status of the selected words, session error counts, and time-ordered raw spelling answers or redacted pronunciation scores. When an exam is created, 0031 writes the term, translations, and IPA into the service-only `learning_exam_word_snapshots` and stores the original word/term with each attempt; on completion it fixes the final error count and whether it was corrected, so later editing or deleting words never rewrites old details. The history endpoint never returns raw Azure audio, user WAVs, provider keys, or full provider payloads. Deleting a course still deletes its session/attempt/snapshot history per the existing cascade rules; this feature is not an undeletable audit store.

## 4. Review, mastery, and Schedule

After finishing a unit for the first time, you can choose 3-, 7-, 15-, or 30-day reviews, none selected by default; records go into `learning_review_schedules` and never create `study_tasks`, so they never earn the task +5. Schedule's Today/This week/All aggregate regular tasks and review schedules together; after entering the corresponding review you can further select any words within the schedule's `all/unlearned` scope, and the schedule is marked complete only after the selected words are done; ad-hoc reviews don't affect schedules.

### 4.1 The single fact and the single projection condition for "learned"

`learning_word_progress.learned_at` is the only database fact for whether a word is "learned". Course cards, the Profile mastered-word count, course 100%, course-completion points, and course badges all read this field or server aggregates derived from it; `initial_*_passed`, the three `*_review_dates` groups, in-session passed, frontend animations, live exam accuracy, and IndexedDB provisional state can never replace it. Since 0033 the product runtime has exactly one condition that can project the null value into a time: **both `spelling_exam_passed_at` and `pronunciation_exam_passed_at` of the same word must be non-null**.

| Exam fact | Condition the server must satisfy | Effect on `learned_at` |
|---|---|---|
| `spelling_exam_passed_at` | The full first round of a spelling exam reaches the configured threshold, and the end-of-round review and all retry words are completed so the session really enters `completed` | Alone it is still not learned; `learned_at` is projected only once the pronunciation exam fact also exists |
| `pronunciation_exam_passed_at` | The full first round of a pronunciation exam reaches the configured threshold, and the end-of-round review and all retry words are completed so the session really enters `completed` | Alone it is still not learned; `learned_at` is projected only once the spelling exam fact also exists |

The order of the two exams is unrestricted; when the second exam passes, the later of the two timestamps becomes the first `learned_at`, and repeated passes never rewrite it. 0035 hardened this relationship from a one-way check into a two-way exact projection trigger: when either timestamp is missing, `learned_at` is forced to null; when both exist, it is forced to equal the later value, and directly assigning any `learned_at` is overwritten too. Clients have no endpoint or table permission to update progress directly.

### 4.2 Reviews only record practice facts and no longer create mastery

1. The Web app starts a session with `mode="review"` from the course card or Schedule. Ad-hoc reviews can choose 1–3 of pronunciation, translation, and spelling plus all words/not-yet-mastered words, then tick any words within that scope; scheduled reviews use the skills/scope saved on the schedule on the server, ignoring values the client re-reports, but allow narrowing the word selection within that scope.
2. Every real answer stores the `local_date` at that moment in an append-only attempt. The date is computed at attempt time in the Profile's valid IANA timezone; changing the time zone later never rewrites history.
3. Wrong answers enter the retry pool. Only when a word is finally answered correctly in the currently selected ability and the whole review session completes does `_learning_advance_session` take the date for that word/ability from the correct attempts, and append it to the corresponding `*_review_dates` only if it isn't already in the array.
4. Completing several reviews on the same day increases `review_count` but never creates a second mastery date. The three abilities can be completed in different sessions on different dates, without requiring all three in the same session; unselected abilities are never advanced along the way.
5. After each review completes, the database only keeps deduplicated dates, increases `review_count`, and completes the linked Schedule; even when all three date groups reach two or more, it never writes exam timestamps or `learned_at`.

A paused, cancelled, or abandoned review session may keep attempts/error facts that already happened, but this session's dates are never added to the review arrays; provider timeouts and microphone failures don't count as correct attempts either. Merely creating 3/7/15/30-day schedules, repeating on the same day, completing the three abilities across days, or completing the initial four stages never marks a word learned.

### 4.3 Both exams together complete mastery

1. The Web app submits the unit, `examKind`, and `examPassPercent` with `mode="exam"`. NestJS only accepts `spelling/pronunciation` and an integer from 1–100 (default 90), forbids linking a Schedule, and forces `scope="all"`. The spelling exam fixes the translation pre-test on; the pronunciation exam fixes Azure pronunciation scoring. Users cannot narrow an exam to the wrong-word scope.
2. The database shuffles this session's items by exam type; since 0031 it can be an owner-validated subset, or the whole unit without a selection. The spelling first round scores by one authoritative spelling result; the pronunciation first round scores by one durable `speech_assessment` result, correct when `PronScore >=` the server's per-word pass mark.
3. The server keeps writing `examAnswered`, `examCorrect`, and the display-only `examAccuracyPercent`. When the first round is fully answered, it fixes `examPassed` with the exact integer condition `examCorrect * 100 >= examRequiredPercent * examTotal`; later retry rounds can neither turn a failed exam into a pass nor change the first-round score.
4. When the first round has wrong words, the session enters the durable end-of-round review state. Even with `examPassed=true`, the user must confirm and finally answer every retry word correctly; once the last retry word is answered correctly the session ends automatically. The trigger writes the practice-completed fact for every exam, but writes the corresponding exam timestamp for the words selected this time only once, and only when `examPassed=true`.
5. When the first round is below the threshold, even if the retry pool is later answered entirely correctly and the session completes normally, the trigger never writes exam timestamps; the user can only start a new exam.
6. The same word can pass either exam first. The first one only changes the corresponding "exam passed" status in the editor; after the second passes, the database sees both timestamps in the same transaction and only then writes `learned_at`. Custom-subset exams only affect the words actually included in that session.

A passed spelling exam back-fills the initial translation/spelling flags, and a passed pronunciation exam back-fills the initial pronunciation flag; neither back-fills `initial_recognition_seen` or any `*_review_dates`. These initial flags are only for learning status display and play no part in 0033's mastery decision. Exams add no new points event type; only when both exams together bring a course with at least 20 distinct normalized words to 100% for the first time does the existing `_refresh_learning_growth` fingerprint rule idempotently award the course +20 and the corresponding badges.

### 4.4 What does not mark, what clears, and what is kept

| Action or state | `learned_at` result |
|---|---|
| Completing the initial recognition/pronunciation/translation/spelling four stages | Not written; initial completion belongs only to the initial session |
| Clicking "I know it", one correct answer, or a frontend instant-correct animation | Not written |
| Creating or completing reviews, completing the three abilities across several dates | Attempts, deduplicated dates, and counts are kept, but it is never written |
| Paused, cancelled, offline-pending sync, revision conflicts, or unfinished sessions | Never written from local predictions; only server-confirmed, completed facts count |
| Passing only the spelling exam | Writes `spelling_exam_passed_at`, but `learned_at` stays null |
| Passing only the pronunciation exam | Writes `pronunciation_exam_passed_at`, but `learned_at` stays null |
| Either exam's first round below the threshold | Even completing later practice does not write that exam fact or `learned_at` |
| Both exams passed and each fully completed | Writes `learned_at`; the completion time of the second pass is the mastery time |
| Cloning a course | The copy's progress starts from zero, and every word has `learned_at=null` |
| Deleting a course/word | Progress cascades with the private content; immutable points/badge history already awarded is kept per the existing rules |

When editing existing words, 0012 keeps the original learning-ability resets, and 0033's `learning_word_exam_mastery_reset` trigger additionally revokes exam facts that may have become invalid, by exam semantics:


| Edited content | Fields reset |
|---|---|
| English `term` changes | All four initial flags, the three review-date groups, both exam timestamps, and `learned_at` are reset |
| translations change | The original translation-ability facts are cleared; `spelling_exam_passed_at=null` and `learned_at=null`, while the pronunciation exam fact is kept |
| IPA changes | The original pronunciation-ability facts are cleared; `pronunciation_exam_passed_at=null` and `learned_at=null`, while the spelling exam fact is kept |
| Only renaming the course/unit, reordering, or moving across units | No exam timestamps, `learned_at`, or ability facts are reset |

### 4.5 Display, growth projection, and security boundary

- `LearningService.listCourses/getCourse` only counts words with a non-null `learned_at` towards `learnedCount`, and `progressPercent=learnedCount/wordCount`; on hover, click, or keyboard focus, the course card toggles between the percentage and "learned/total".
- `learning_profile_summary` counts `learnedWords` deduplicated by normalized English; the same English word in several courses counts only once.
- `_refresh_learning_growth` recomputes course 100%, the nine-tier badges, and the course +20 after a session completes; only words with a non-null `learned_at` take part. A course needs at least 20 distinct normalized words, and the points business key is still the SHA-256 of the user plus the sorted word set, so the same word set cannot be claimed again by deleting, recreating, or cloning.
- `learning_word_progress` only allows owner SELECT for ordinary clients; INSERT/UPDATE/DELETE and the internal `SECURITY DEFINER` functions/RPCs are not granted to public/anon/authenticated. The Web app's accuracy, retry pool, and completion screens are display only; server transactions are authoritative.

## 5. Growth facts

Profile aggregates the number of learning courses, the number of mastered English words after normalized deduplication, the number of distinct review dates, and the course badges already durably awarded. Badge thresholds: Vocabulary Walker 20/200/1000, Course Graduate 1/5/20, Review Keeper 3/15/50.

A course with at least 20 distinct normalized English words at 100% mastery earns +20 points the first time. The business key is built from the user ID and the SHA-256 of the sorted deduplicated word set and is awarded through the existing `point_entries/point_event_states`; deleting, recreating, or cloning the same word list cannot claim it again. **Deleting a course** does not rewrite point entries or badge history that already happened; deleting an account cascades the account's ledger and badge awards per the privacy process.

## 6. Sharing, market, and governance

- Share tokens are 32 random bytes, with only the SHA-256 stored; the public JSON removes private course/unit/word IDs, progress, and internal fields, and the React display layer escapes text uniformly. Authors can list, revoke, or create new tokens, and signed-in users with the link can clone for free.
- Market publishing stores immutable version snapshots; after updating the source course, a new version must be published explicitly. Every clone is an independent private snapshot with progress starting from zero and keeps the source/author attribution; cloned courses cannot be shared or listed again.
- The first version is "Free" only and does not read or write credits, orders, or payments. Publishing/reporting has server-side daily limits; reaching the report threshold only alerts and never auto-delists. Configured administrators can hide/restore publications through RPCs with audit records.
- HTML is escaped in the display layer; authors confirm content rights before publishing. Sharing and market tables are not exposed to anonymous PostgREST, and public reads only go through NestJS.

## 7. Azure Speech, privacy, and degradation

TTS and en-US scripted pronunciation assessment live in the server adapter layer, and the reference text can only be derived from `wordId/sessionId` in the current user's course. The server limits scoring input to at most 8 seconds, 2 MB, 16 kHz mono WAV; the browser records at most 6 seconds with echo cancellation, noise suppression, and auto gain control off, and no longer does VAD, volume thresholds, minimum "clear speech" checks, leading/trailing silence trimming, or content truncation. The Web app only does the 16 kHz/16-bit/mono PCM wrapping that Azure's format requires, and Nest forwards the same bytes to Azure after validation. Recordings are only forwarded in request memory and discarded after the response; the database only stores scores, error types, and phoneme feedback. Synthesized audio is shared across courses in private Storage by a normalized content key, and user recordings are never cached.

Scoring uses HundredMark, Phoneme, IPA, and miscue; phonemes below 70 are marked red in the UI. The overall pass mark is controlled by `AZURE_SPEECH_PRONUNCIATION_PASS_SCORE`, default 70 and required to be 1–100; the API returns `passThreshold/passed/queuedForRetry`, the 0014 transaction updates the recognition retry pool by the overall `PronScore`, and clients cannot self-report passing. Scoring is still optional: not scoring never blocks learning, while a low score after actively scoring requires seeing that word again in this stage's retry round. Each user defaults to 30 per minute and 300 per day, with a monthly budget and a circuit breaker on top. When Azure is unavailable, TTS degrades to browser speech and scoring is disabled, and provider/microphone failures never count as learning errors.

0015 adds a monotonic `revision` to sessions, and a client UUID, unique constraint, and first-response snapshot to attempts. The Web app first gives feedback in the current render frame from the answers already in the session: correct answers advance automatically after about 520 ms, and wrong answers stay until a manual "Next question"; in the background it submits the IndexedDB outbox serially by revision. The API returns `sessionPatch`, so ordinary answers no longer refetch the full Session/Courses; duplicate attempts replay idempotently, and after a 409 conflict it fetches `learning_get_session_snapshot` once. A completion predicted offline only shows "Waiting to sync"; the server still alone decides the retry pool, cursor/stage, progress, error counts, points, and badges. Signing out clears this account's outbox, which can never be submitted across accounts.

0015 also keeps `vocabulary-audio` in private Storage as the single server-side source of truth and adds the `learning_audio_assets` durable queue with no client permissions. The global key is `SHA-256(normalizedTerm + locale + voice + format + synthesisVersion)`; starting a session queues the whole unit, and an audio miss only raises its priority and quickly returns `202 AUDIO_PENDING` without waiting for Azure inside the request. The worker defaults to single concurrency, at least 3.1 seconds between requests, 20 per minute, and 500,000 characters per month. The Web app reads Cache Storage first; since the 0017 application fix, the current word and the next four words, whether ready or pending, are proactively cached or have their queue priority raised with at most two concurrent requests; the manifest is polled every three seconds, and once ready the audio is stored in Cache Storage immediately and the stale browser-speech notice for that word is cleared. Users can still download/resume/delete specific units; this does not include a full offline app shell. Storage network failures must fail explicitly; only HTTP 404 or Storage HTTP 400 + JSON `statusCode=404` count as a normal miss, so failures never cause repeated Azure calls.

### 7.1 OpenRouter translation pre-test boundary

The translation pre-test is not Courses AI file import and not client-side fuzzy matching. The browser only sends the current session/word, revision, UUID, and user input; NestJS takes the English and translations from the owner-visible course. When the normalized input exactly equals any reference translation, versioned server rules judge it correct deterministically without calling the provider; only non-literal synonyms/paraphrases call the free `nvidia/nemotron-3-super-120b-a12b:free` in JSON Object mode, forcing the Nvidia upstream, forbidding fallback, and turning reasoning off. NestJS locally requires exactly one `{correct:boolean}` field, and extra/missing fields, wrong types, and bad JSON all fail closed. The model only decides the non-literal semantic boolean, and the API uses fixed safe teaching copy as feedback; neither path can advance the session, award points, or rewrite reference answers on its own.

`learning_spelling_translation_assessments` only stores the SHA-256 of the user's answer, provider/model, the verdict, token usage, the lease, `quota_counted/quota_counted_at`, and the first response; the input text only exists in API request memory. Replays with the same UUID/answer hash return the first response directly; a wrong translation atomically writes one spelling error with the same UUID, and a correct translation requires the subsequent spelling attempt to reuse that UUID. Timeouts, network failures, or a missing valid boolean twice release the lease without recording an error; an invalid structure on the first HTTP 200 can retry once within the same 12-second total budget, and empty feedback falls back safely without discarding the boolean.

0027 separates "claiming an idempotent lease" from "consuming provider quota": exact normalized matches, completed replays, and merely creating pending/processing rows don't use quota; only when NestJS is about to call the real OpenRouter does it atomically write `quota_counted=true/quota_counted_at=now()` under a per-user advisory lock. Both the minute and 24-hour windows are computed from this real reservation moment, not from the possibly earlier assessment creation time. Provider/network retries with the same UUID don't consume product quota again. The defaults are 20 per minute and 500 per rolling 24 hours per user; reaching either limit returns its own stable error code with an exact `retryAfterSeconds`, and the Web app shows the expected recovery time. A real provider failure has already made an external request, so that quota fact is kept, but the judgement lease is released and no learning error is recorded; production fakes are explicitly forbidden.

The UI countdown and instant states are not server facts: timeouts still go through the authoritative attempt RPC, and the result page shows the correct English and the split translations whether right or wrong. Enabling it in production requires a one-off database RLS/idempotency gate, a fake-provider Chromium flow, and a separate real OpenRouter JSON Object + local schema/API gate.

### 7.2 Fish Audio translation voice input boundary

0037–0038 are enabled in production: only the translation input of translation-first spelling offers a microphone, and NestJS pins `fish-audio/transcribe-1` and `language=zh`; before the provider call, a service-role-only RPC validates the owner, active session, spelling stage, `translationFirst`, revision/current word, and reserves the minute/local-day/month budgets independently. The recognition result only fills editable text and is never auto-submitted or graded; late results that no longer match the current question are discarded by the Web app. WAVs/transcripts never enter PostgreSQL, Storage, Cache, backups, or business logs; only `translation_stt` quota facts are persisted.
